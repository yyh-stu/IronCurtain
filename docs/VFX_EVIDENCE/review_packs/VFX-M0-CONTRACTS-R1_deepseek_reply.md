## 提案 1:SettledDamage 结算后事件

**结论:修改后放行**

**风险 / 缺失字段:**

- **顺序依赖风险(建议级)**:材料明确"同 tick 末按受害者聚合……之后统一判死发 `EntityDied`"。提案只说"结算结束后"发 `SettledDamage`,但**没有声明它与 `EntityDied` 的先后**。若 `SettledDamage` 在 `EntityDied` 之后发,消费者可能拿到已死亡/已移除实体;若之前发,则消费者无法从该事件判断生死。这是隐藏的顺序依赖,必须显式钉死。依据:现有事实"之后统一判死发 `EntityDied`"。
- **受害者已死亡/已移除的语义缺口(建议级)**:字段只有 id 与盾/血前后值,没有"该受害者本 tick 是否死亡"或"实体是否仍存活"的标记。消费者要判断生死只能再去监听 `EntityDied` 并自行关联,存在跨事件关联成本与竞态。建议补一个 `DiedThisTick` 布尔或明确"本事件保证在 `EntityDied` 之前发出"。
- **"仅对盾或血发生实际变化的受害者各发一条"的边界未定义(建议级)**:若某受害者被攻击但盾血均无变化(例如被完全免伤/乘子归零),按字面不发事件——这符合"实际变化"表述,但需确认这正是意图,否则消费者会漏掉"被打了但没掉血"的情形。材料未说明。
- **签名兼容性**:纯新增事件,不触碰既有签名,符合约束。**放行前提**是上述顺序与生死语义补齐。

**更小的替代方案**:若目的只是"事后读最终盾/血",现有事实已说明"盾/血的最终变化只能事后读字段",即消费者本可自行读字段。若新增事件仅为省去轮询,可考虑只暴露一个"本 tick 结算摘要"的只读查询,而非新增事件流——但这是取舍,不构成驳回理由。

**需补充信息**:`SettledDamage` 与 `EntityDied` 的发出顺序;死亡/移除实体的处理约定。

**更小的替代方案**:若只需让特效知道"脉冲发生了",可发一个专用只读事件(如 `PulseFired`),避免污染 `DamageDealt` 的 AttackerId 语义。这是更小、更干净的替代。

**需补充信息**:`DamageDealt` 现有消费者清单;脉冲伤害是否进入同 tick 聚合;AttackerId 取值域契约。
