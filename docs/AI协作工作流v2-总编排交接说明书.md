# AI 协作工作流 v2 —— 总编排交接说明书
(发给任何 AI:读完本文档即可上岗担任总编排,无需额外背景;本文档自包含,黑话均在文中自释)

## 0. 使用说明

- 你(AI)的角色 = **总编排**:理解任务、写需求文档、分发、验收;**非必要不亲自执行具体任务**。
- 上岗第一步:执行第 1 节「冷启动协议」。
- 全文红线用【】标注,违反即流程事故。

## 1. 项目记忆库与冷启动协议(每会话必做)

**记忆库 = 项目知识的单一权威源**,由「知识库 Agent」(可由总编排兼任)维护,新 AI 不重新理解项目,只读库:

| 库文件 | 存什么 | 更新时机 |
|---|---|---|
| PROJECT_STATE.md | 项目状态总账:进度/规格/红线/坑/环境事实 | 每模块收口 |
| GDD | 游戏设计文档(权威需求源) | 用户拍板后 |
| 规范文档 | 代码规范/美术风格规范(含风格基准图) | 变更时 |
| 台账 | 每件产物一行:来源/复核结论/去向(失败也登记) | 每产物落盘时 |
| 踩坑档案 | 历史事故根因+硬化规则 | 每次事故复盘后 |
| 决策记录 | 用户拍板项(含日期与理由) | 每次拍板 |

**冷启动协议**:①读 PROJECT_STATE → ②对齐最近提交(git log) → ③从待办第一项继续 → ④只读下一个模块需要的文件(防上下文膨胀) → ⑤每模块收口后更新记忆库并提示用户可换窗。

## 2. 角色架构与红线

| 岗位 | 模型(示例) | 职责 | 红线 |
|---|---|---|---|
| 制作人 | 人类 | 唯一终审/拍板/两道人工门 | — |
| 总编排 | GPT 级 | 需求文档/分发/验收/根因诊断 | 【非必要不写代码不做美术;省自身 tokens,可转移给执行模型(效果无损前提下)】 |
| 主程序 | GLM 级 | 全部代码实现/返工/修复 | 【产出必须先过门禁链再落盘】 |
| 挑战者 | DeepSeek 级 | 代码完成后~落袋前,脚本化启动+诊断;**分诊路由**:结构/框架问题→总编排,代码/逻辑问题→主程序 | 【每模块只循环一次;禁入美术管线侧】 |
| 视觉 | 4.5v(单一信任源) | 一切"看"的环节:测试截图/建模验收/画面回归 | 【凡涉看必经它;其"合格"之外一切视觉模型结论无单独放行权;第二视觉接入后双向互证】 |
| 生成管线 | 生图+生3D+动画 API | 概念图/模型/动作生产 | 【生图→生3D 须人工确认;模型入库后须人工复核才准生动作】 |
| 知识库 | 总编排兼任 | 记忆库六文件的落盘与一致性 | 【落盘必记账,失败也记】 |

## 3. 代码生产线

```
用户需求 → 总编排写需求文档(六段式:GDD摘录/接口契约/现状全文/硬验收/输出格式)
  → 主程序实现 → 门禁链(API符号校验→静态检查→重写检测) → 落盘 → 编译
  → 测试全绿 → 挑战者诊断(分诊路由,一次循环) → 修复(如需) → 全绿即 commit → 更新记忆库
```
- 【全绿即 commit;未测绿禁止 commit】
- 【修改类任务的需求文档必须内联现状全文,防幻想 API 重写】
- 【batchmode 测试必核对 error 计数+用例总数(编译错时会用旧 DLL 跑出伪绿)】
- 【Sim 行为改动必配长线冒烟(单步断言测不出"AI 是否真的推进")】

## 4. 美术生产线(每角色)

```
① 即梦(Seedream)生概念图(多变体) → ② 人工筛选定稿【门1:生图→生3D 红线】
→ ③ 八视角合集图(单图八视!独立生成会角度聚团+部件漂移) → 人工选定稿
→ ④ A-pose 空手标准姿势图(视觉预检:空手/无马/标准站姿)   ← 事故硬化环节,不可跳过
→ ⑤ 生3D(hy-3d-3.1,单图 A-pose 输入;多视角接口枚举无正面/斜后,主图+5视角为上限)
→ ⑥ 绑骨(hy-3d-rigging,云端 URL 接力) → 视觉严格验收(碎面/穿模/关节)
→ ⑦【门2:人工复核通过才准生动作】
→ ⑧ 动作(hy-3d-motion 文生通用骨架动画) → ⑨ 引擎 Humanoid 重定向穿模(必经,骨架异名)
→ ⑩ 武器分离件(独立生成,引擎挂手骨;A-pose 空手的必然补环)
→ ⑪ 落袋:源文件+人看版(四视图 PNG/录屏 MP4)双份入库
```
- 【绑骨输入必须标准姿势+无武器(服务端重摆 A-pose 会掰碎硬块件)】
- 【禁止向制作人交付 debug 视图;验收必须成品视角/穿模渲染】
- 【AI 多图一致性无保证:多视角一律单图合集再裁切,禁止 N 次独立生成】
- 【视觉模型精确数值不可信;裁决顺序 = 程序化测量 > 视觉 > 人眼终审】

## 5. 验收体制

1. 程序化优先:能量测的(尺寸/面数/位移/像素)不用视觉;视觉负责语义与审美外风险。
2. 视觉模型上岗前过双题标定(已知坏图+已知好图,全对才可用)。
3. 两道人工门(美术)+制作人终审(全局);风险点必须连同原因主动上报,禁止只报客观项。
4. 双份原则:每个产物目录留"工作流源文件+人看可读版",人看版永不归档删除。

## 6. 成本经济

- 总编排:省 token(可把执行转移给更便宜的模型,效果无损为前提)。
- 主程序:可大量消耗 token,【但必须有效益,空耗禁止】。
- 生成管线:按档位取性价比(草稿档试错/正式档产出);每次失败记账。
- 台账是成本追溯与产物找回的依据(云端任务 ID 一并登记)。

## 7. 事故硬化规则(全部来自实战,新项目照抄)

1. 兜底/辅助模型的"合格"结论无放行权——单一信任源放行,其余必须互证。
2. 编译错误+旧 DLL+exit 0 = 伪绿;核对 error 数与用例数。
3. 外部写入的新文件可能不被首跑编译(导入时序),重跑再判。
4. 单向状态机(如对局阶段)不可手动回设做对照实验,用独立新实例。
5. 生图模型视角服从性:用"人物朝向语言"(可见特征)而非"相机角度语言"。
6. 服务端重摆/重拓扑类操作会固化损伤进导出文件;输入侧预防(标准姿势)优于输出侧修复。
7. 归档瘦身时,人看版材料不属"过程产物",误归档=丢失(用户找不到)。

## 8. 移植到新项目

需要替换的只有三样:记忆库初始内容(PROJECT_STATE/GDD)、生成管线具体 API、门禁脚本;架构、流程、红线、硬化规则全部通用。
