# 铁幕:前线 项目介绍与 K3 总编排需求(档位咨询)

> 用途:整段粘贴给 Kimi(K3)提问。已自包含,不依赖任何外部文件。

## 一、项目概况

- **项目**:《铁幕:前线》单机即时战略(RTS)游戏 Demo,Unity 6000.0.30f1 LTS + URP 17。
- **目标**:把 1.6 版游戏设计文档做成单线闭环可玩 Demo,完成度介于"产品级与 demo"之间,打磨后可发布。
- **代码架构**:纯 C# 确定性逻辑层 Sim(约 25 个系统文件,10Hz 固定步长、不依赖 Unity 引擎)+ View 表现层 + 188 条 EditMode 断言测试(全绿)。
- **开发方式**:AI 编排流水线——总编排(技术总监)拆解需求、派单给程序主程(GLM-5.3)生成代码,经三层门禁(API 符号检查/静态检查/重写检测)后编译,跑 188 条断言回归,全绿即提交。
- **当前进度**:战斗核心/生产占领/升级/海克斯/视野/AI/连续坐标大地图/将兵制(兵团系统)/撤退等已全部完成并全绿;剩余约 8–12 个模块(镜头迷雾小地图、战斗 UI、特效音效、对局计时结算、美术批量生成、收口打包),预计剩余工期 2–3 个月。

## 二、K3 要担任的角色:技术总监(总编排)

职责:
1. **需求拆解**:把制作人拍板的需求拆成可验收的模块任务单(六段式:角色与任务/需求规范/输入现状/输出格式/硬验收/禁止项)。
2. **派单**:给程序主程(GLM-5.3)写代码生成提示词,内联目标文件的现状源码全文。
3. **门禁与验收组织**:组织三层门禁 → 编译 → 188 条断言回归;失败时做根因分析、写可执行的修复任务单(每模块 ≤3 轮)。
4. **文档维护**:项目状态文件、协议、归因台账。

不做什么:不写业务代码(全部由 GLM-5.3 生成)、不做审美裁决(归制作人)、不与其他模型直接对话(全部经总监中转)。

## 三、工作负载特征(决定档位的关键)

- **输入重**:每轮编排要重读项目状态文件(约 500 行规格)+ 模块拆解文档 + GLM 输出全文;单轮 6–10 万 tokens,输入占 85% 以上,输出仅 2–10k。
- **高频重读**:项目状态/协议/数值表每个模块都会被反复重读 → 缓存命中率天然高。
- **会话节奏**:每 1–2 个模块开一个新会话(防上下文膨胀);每个模块周期约 2–4 个长会话,每会话 10–30 轮编排交互。
- **历史实测**:近 6 个模块(现由 GLM 自任编排)每模块平均 1–2 次代码生成调用(每次约 7 万 tokens)+ 0–1 个修复轮;编排交互 token 量约为代码生成的 3–5 倍。
- **剩余总编排量粗估**:5–10M tokens(输入为主),分散在 8–12 个模块周期。
- **已知社区实践**:有开发者用"K3 主编排 + GLM-5.3 主程序"跑同类 AI 编排流水线项目,与我们的架构同构。
