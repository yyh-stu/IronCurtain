# 专家团编排协议(PROTOCOL)

> 定位:技术总监(主编排,2026-09-06 起由 GLM-5.3 兼任)调度全部专家的规则;deepseek-v4-pro 任**逻辑挑刺岗 LogicAuditor**(2026-09-06 制作人拍板常驻;窄口径=逻辑/时序/状态类审查,API 存在性类归 api_gate+编译器)。核心原则:**审美与取舍归制作人,创作归专家,正确性归验收层,调度归总监;模型间不对话,证据链说了算(编译器/断言/现状源码 grep 裁决一切争议,挑刺只产出"待验证线索"不产出"意见")。**

## 1. 任务流转(标准循环)

```
制作人授意(目标/拍板)
   ↓
总监拆解 → 写任务单(见 §3 格式) → 派给对应专家
   ↓
专家产出(按角色卡输出格式)
   ↓
验收层检查(正确性/一致性/断言)
   ↓
通过 → 上报制作人审(手感/审美终审)
失败 → 总监分析根因 → 修复任务单丢回专家(≤3 轮)
       连续 3 轮失败 → 总监上报制作人,重新拍板需求(大概率是需求本身错了)
```

## 2. 分权红线(违反即流程事故)

| 事项 | 唯一有权者 |
|---|---|
| 审美/画风/手感裁决 | 制作人(人) |
| 代码与数值实现 | 程序主程(GLM-5.3),**总监不写业务代码** |
| 需求拆解/派单/根因分析 | 技术总监 |
| 风格规范(参考图/色板)制定 | 美术总监(生成)→ 制作人终选 |
| "好不好看" | 制作人;视觉验收只答"符不符合规范/有没有错" |
| "能不能玩/顺不顺手" | 制作人试玩 |

## 3. 任务单格式(总监→专家的派单,六段式)

1. **角色与任务**:你是[角色卡名],本任务只做 X
2. **需求与规范**:制作人拍板的内容摘录(风格规范/数值表/验收标准)
3. **输入**:给你的现状文件全文(代码任务必须内联目标文件)
4. **输出格式**:文件路径/结构/标记(如 `// FILE:`)
5. **硬验收**:可机器裁决的清单(编译通过/断言/颜色值/尺寸)
6. **禁止项**:不做什么、不碰哪些文件

## 4. 验收矩阵

| 产出类型 | 验收方式 | 验收者 |
|---|---|---|
| Sim/View 代码 | 编译 + EditMode 断言(现有 188 条+新增) | TestQA |
| GLM 交付输出 | **deepseek 挑刺(deepseek_review.py,逻辑/时序/状态类)→ 总监逐条裁决(证实/证伪+证据)→ review_check.py 过闸后才允许 parse_files 落盘**;提示词定稿前同流程审一轮 | LogicAuditor(deepseek-v4-pro)+ 总监裁决 |
| 画面/渲染 | 截图 → 对照风格规范查一致性 | VisualQA → 制作人终审 |
| 交互流程 | Play 实测:输入→输出正确且无延迟感(黑盒,不看实现) | 总监操作+VisualQA 记录 |
| 玩法/数值设计 | 结构文档评审(是否自洽、覆盖边界) | 总监+制作人 |
| 资产生成 | 模型文件完整、可导入、贴图正常 | 程序主程导入反馈 |
| 音效 | 可播放、无爆音、时机正确 | VisualQA |

## 5. 专家间交接格式

- 专家之间**不直接对话**,全部经总监中转(防多模型互相污染上下文)。
- 交接物:任务单(输入)+ 产出文件(输出)+ 验收结论(通过/失败原因)。
- 失败原因必须写成**可执行的修复指令**(指出文件/行/现象),禁止"感觉不对"这类描述。

## 6. 模型接入位(待用户提供 API)

每个待接入专家在角色卡中标注 `模型:待接入`。接入后总监按 ROSTER.md 封装调用脚本,并在此处登记:端点/key 位置/额度限制。
